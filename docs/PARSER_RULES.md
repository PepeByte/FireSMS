# Parser Rules

Parser rules teach FireSMS how to recognize an SMS and convert it into a Firefly III transaction.

## Rule matching order

FireSMS loads enabled parser rules ordered by priority. For each incoming SMS:

1. `senderPattern` must match the SMS sender.
2. `bodyPattern` must match the SMS body.
3. `amountTemplate` must resolve to a positive number.
4. The first successful rule produces a transaction.

A misconfigured rule (invalid regex, unknown group, invalid date format) never stops processing: it simply does not match, and the next rule is tried. The rule editor and the JSON importer reject these mistakes before saving.

Multi-part (long) SMS messages are joined into one body before matching.

## Rule fields

| Field | Meaning |
|---|---|
| `id` | Stable rule ID. Can be generated by the app. |
| `name` | Human-readable rule name. |
| `enabled` | Whether the rule is active. |
| `senderPattern` | Regex matched against the SMS sender. |
| `bodyPattern` | Regex matched against the SMS body using `DOT_MATCHES_ALL`. |
| `amountTemplate` | Template used to produce the amount. Usually `{{amount}}`. |
| `descriptionSource` | Either `template` or `regex_group`. |
| `descriptionValue` | Static text, template, or group name depending on source. |
| `sourceAccountName` | Your own Firefly account (see [Accounts](#accounts)). |
| `sourceAccountId` | Firefly ID of your own account, set when it is picked from the list. |
| `sourceAccountKeyword` | Optional. When no own account is set, the first SMS word containing this keyword (punctuation stripped) is used as your account name. |
| `destinationAccountName` | The other party: merchant, payer, or the receiving account of a transfer. |
| `destinationAccountId` | Firefly ID of the other party, set when it is picked from the list. |
| `type` | `withdrawal`, `deposit`, or `transfer`. |
| `priority` | Lower values are tested first. |
| `datePattern` | Optional regex or `{{groupName}}` for transaction date. |
| `dateFormat` | Java `DateTimeFormatter` pattern for `datePattern`. |
| `remarksPattern` | Optional regex (searched within the matched text) or `{{groupName}}` for notes. Used only when `remarksTemplate` is blank. |
| `remarksTemplate` | Optional notes template. Takes precedence over `remarksPattern`. |

## Regex syntax

FireSMS uses Kotlin/Java regular expressions.

Use named groups like this:

```regex
(?<amount>[0-9,]+(?:[.][0-9]{1,2})?)
(?<merchant>[A-Za-z0-9 &.-]+)
(?<date>[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2})
```

Group names should begin with a letter and use letters/digits. Avoid punctuation in group names.

## Templates

Templates reference named groups with double braces:

```text
{{amount}}
{{merchant}}
Payment to {{merchant}}
```

Every placeholder must name a group in `bodyPattern`; the editor refuses to save a rule that does not. If an optional group does not participate in a match, its placeholder becomes empty text. A description that ends up blank falls back to the rule name.

Amounts are cleaned by removing everything except digits and dots (so `Rs.1,234.50` becomes `1234.50`). If the result is not a positive number, the rule does not match.

## Accounts

A rule names two accounts. The editor labels them by what happens to the money, and FireSMS puts them on the side Firefly III expects:

| Type | Editor fields | Firefly source → destination |
|---|---|---|
| `withdrawal` | **Paid from** (your account), **Paid to** (optional) | your account → merchant |
| `deposit` | **Received into** (your account), **Received from** (optional) | payer → your account |
| `transfer` | **Moved from** (your account), **Moved to** (your account) | your account → your other account |

The editor shows the result as a line such as `In Firefly: Checking → Example Store`.

Both fields search the accounts in Firefly III, showing only types that fit: asset accounts and liabilities for your own account; expense accounts for a payee; revenue accounts for a payer; your own accounts for a transfer target. A check below each field shows whether the name was found:

- **Found in Firefly**: the rule stores the account's ID, so it keeps working if the account is renamed.
- **Not in Firefly yet**: allowed for payees and payers; Firefly III creates the account with the first transaction.
- **Not one of your Firefly accounts**: your own account and a transfer target must already exist, so the rule cannot be saved.

Your own account is required, either picked from the list or taken from the SMS with the account-word option. A transfer also needs its target. If Firefly III cannot be reached, names are saved as typed without checking.

Rules created before these fields existed sometimes stored a deposit's own account as the destination; FireSMS reads those as your own account.

## Transaction types

Use one of:

- `withdrawal` for spent/debited/paid transactions,
- `deposit` for credited/received/refund transactions,
- `transfer` for movement between owned accounts.

## Dates

If `datePattern` and `dateFormat` are blank, FireSMS uses the SMS received timestamp.

If present, both fields must be set.

Example body group:

```regex
(?<date>[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2})
```

Rule fields:

```text
datePattern = {{date}}
dateFormat = yyyy-MM-dd HH:mm:ss
```

The date is parsed with a Java `DateTimeFormatter` pattern, in English, in the device time zone. Month and AM/PM names are matched case-insensitively, so `MMM` accepts `Mar`, `MAR`, and `mar`.

Date-only formats such as `dd/MM/yy` are supported: the SMS received time of day is kept. If the date cannot be parsed, the SMS received timestamp is used.

## Importable AI JSON format

The rule editor can import a subset of rule fields from JSON. The user still configures identity, sender pattern, account mapping, and priority in the app.

Import JSON must contain exactly these fields:

```json
{
  "bodyPattern": "",
  "amountTemplate": "",
  "descriptionSource": "",
  "descriptionValue": "",
  "type": "",
  "datePattern": "",
  "dateFormat": "",
  "remarksPattern": "",
  "remarksTemplate": ""
}
```

All fields are strings. Optional fields should use an empty string, not `null`.

## Example

Sanitized SMS:

```text
A/C XX1234 debited by USD 12.34 at EXAMPLE STORE on 2025-01-31 14:30:00 Ref ABC123.
```

Importable JSON:

```json
{
  "bodyPattern": "A/C (?<account>[^ ]+) debited by USD (?<amount>[0-9,]+(?:[.][0-9]{1,2})?) at (?<merchant>.*?) on (?<date>[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}) Ref (?<ref>[A-Za-z0-9]+)",
  "amountTemplate": "{{amount}}",
  "descriptionSource": "template",
  "descriptionValue": "{{merchant}}",
  "type": "withdrawal",
  "datePattern": "{{date}}",
  "dateFormat": "yyyy-MM-dd HH:mm:ss",
  "remarksPattern": "{{ref}}",
  "remarksTemplate": "Reference {{ref}}"
}
```

After importing, configure a sender pattern such as:

```regex
BANKNAME|VM-BANK
```

## Testing rules

Use the rule editor's preview/test action with sanitized sample messages. Parser changes in code should include unit tests under:

```text
app/src/test/java/com/firesms/app/domain/parser/
app/src/test/java/com/firesms/app/domain/rules/
```

## Privacy reminder

Do not paste real bank SMS messages into public issues, documentation, tests, screenshots, or external AI tools without redaction.
